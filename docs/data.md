# ROM data: structure, not bytes

This page is the convention for the ROM's data (issue #36). The code side
of the project is finished (every game function is byte-exact C, see
AGENTS.md). The data side works differently, because of the data policy.

## 1. The policy

The repository is public. The rule is in AGENTS.md ("Data policy"). It
follows the zeldaret/mzm line, which was chosen after comparing what the
other decompilations do with the ROM's data (surveyed on #36):

| project | data not yet understood | tables a consumer proves | graphics, audio, text, maps |
|---|---|---|---|
| katam (Kirby & The Amazing Mirror) | label + `.incbin "baserom.gba"` slices | committed as C with values | committed, converted (PNG, MIDI, AIF) |
| pret (pokeemerald ...), sa2, fireemblem8u | a few baserom slices, or none | committed as C with values | committed, converted |
| tmc (Minish Cap), mzm (Zero Mission) | none left | committed as C with values | **not committed**: extracted from the baserom at build time (tmc's JSON asset manifests, mzm's `tools/extractor.py`) |
| sm64, OoT (N64) | - | committed as C | **not committed**: extracted from the baserom at build time |

So this project draws the same line as tmc, mzm, sm64 and OoT:

- **Assets are never committed, in any form.** That covers graphics
  (tiles, tilemaps, palettes, sprite frames), audio (samples, songs), text
  and fonts, and level layouts and maps. They stay `.incbin
  "baserom.gba", <offset>, <length>` slices, read from the user's own
  dump. If they are ever made editable, that happens through build-time
  extraction into gitignored directories, never by committing converted
  files.
- **Functional data may be committed as C** once a decompiled consumer
  proves its layout: pointer tables, task/actor/object definitions,
  animation and frame tables, parameters. It gets typed, named fields,
  exactly like the decompiled code.
- **Until then, data is committed as structure only**. That is what
  `make split` emits today, and what the rest of this page describes.

What a data change commits is *structure*:

- **labels** at table boundaries, so C references a real definition
  instead of an absolute `gUnk_08XXXXXX = 0x08...`;
- **pointer words as symbols**: `.word gUnk_0835DDC0`, `.word sub_0806xxxx+1`.
  A pointer says where a table points, which is structure, not content.
  It is also what will make the ROM shiftable (§6);
- **types**: C declarations proven by the decompiled consumers (phase 2);
- **build-time extraction**: every other byte stays
  `.incbin "baserom.gba", <offset>, <length>`, read from the user's own
  dump when the ROM is built. Only offsets and lengths are committed.

## 2. What `make split` emits for a data segment

Every `data`-kind row of `docs/analysis/segments.txt` (except the
hand-written cartridge header `asm/rom_header.s`) is configured in
`tools/split_config.json` and emitted by `tools/split.py` as
`data/<segment>.s`. `asm/` holds code only. A generated data file contains
nothing but:

```
@ Auto-generated by tools/split.py from baserom.gba - DO NOT EDIT.
@ ... header: range, counts, the asset note ...
	.section .room_bg_anim_lists, "a"
	.global	room_bg_anim_lists
room_bg_anim_lists:
	.global	gUnk_087E1E78
gUnk_087E1E78:
	.word	gUnk_083356E0
	...
	.incbin	"baserom.gba", 0x7E1EA0, 0x4
```

The emitter's rules, in order:

1. **Labels.** A `.global` label at every ROM `data_symbols` value and
   every `extra_labels` address inside the segment. Their absolute
   definitions leave `asm/rom_syms.s`, which keeps only RAM/I-O cells
   (and would list a ROM table only while it waits for its label).
   Several names at one address are fine (`gUnk_080CFE20` and
   `gSramIdString`).
2. **Code pointers.** A 4-aligned word whose value is a
   `docs/analysis/symbols.csv` function entry becomes `.word <fn>+1`
   (Thumb, value odd) or `.word <fn>` (ARM, value even), in every segment
   that is not an asset (§4). An even value equal to a *Thumb* entry is a
   `mov pc` jump-table target (lesson 4.38), and a relocation against a
   C-defined Thumb function would set bit 0, so it is never symbolized.
3. **Data pointers**, only inside a `pointer_tables` entry: a table whose
   layout a decompiled consumer proves (§5), or whose element type the
   consumer declares and whose extent is the span up to the next label
   (§5.1). Every non-NULL pointer word of it must resolve to a function, a
   ROM data label or a named RAM cell; `make split` stops on the first
   unresolved one (§3.2). NULL words stay inside the `.incbin`.
4. **Everything else** is `.incbin`, whatever its length (four bytes of a
   count between two pointers included).

A word that would need a label strictly inside it (at `addr+1..addr+3`)
stays inside the `.incbin`; inside a pointer table that is an error.

The verification is the one every split file gets: the whole group is
assembled, linked at the segments' VMAs with `asm/rom_syms.s` and
stand-ins for C-defined symbols, and compared with the baserom. A data file
cannot fall back to raw bytes (there are no instructions to demote), so a
mismatch is a planning bug and stops the run. `make compare` remains the
real proof (lesson 4.116: the stand-ins also resolve names the real link
cannot).

## 3. Adding structure

All of it goes through `tools/split_config.json`, never through the
generated files: CI re-runs `make split` and fails on any diff under
`asm/` or `data/` (lesson 4.11).

### 3.1 A label

Add `"0xADDRESS": "gUnk_ADDRESS"` to `data_symbols` (sorted by address;
`tools/addsyms.py` does this from a link's `undefined reference` wall).
A ROM address inside a data segment becomes a real label with the next
`make split`. Renaming (`gUnk_` to a real name) is #155's job; the address
is the key, so a rename is one value change.

### 3.2 A pointer table

Add an entry to `pointer_tables`:

```json
{
  "start": "0x087E1F58",
  "end": "0x087E2570",
  "why": "the stage room lists gUnk_087E1D58[level][stage] points at: ...",
  "targets": {
    "pointers": ["0x08", "0x0C", "0x10", "0x18", "0x1C", "0x20",
                 "0x28", "0x2C", "0x30", "0x44", "0x48"],
    "why": "struct RoomDef (0x58 bytes, M07, src/room_27e28.c): ..."
  }
}
```

- `start` plus `end` or `count`; `stride` (default 4) and `pointers`, the
  byte offsets of the pointer fields inside one element (default `["0x0"]`),
  describe an array of records: the task-type table is
  `"count": 266, "stride": 8, "pointers": ["0x4"]`.
- `why` is required: the consumer that proves the layout (function and
  file, or a pret reference for SDK tables). A table whose layout no
  decompiled code proves does not go in, however pointer-like its words
  look (§5).
- `targets` (optional, one level) says that every non-NULL word of the
  table points at one record of this layout, whose pointer fields are
  pointer words too. The room lists use it for their `RoomDef` headers.
- `"extent": "next-label"` replaces `end`/`count` for a plain array of
  pointers whose length no consumer gives (§5.1). Its `why` cites the
  declaration (`file:line` and the `extern`).
- A table that has moved to C (§5.2) keeps its entry: its own words are
  not emitted (they are C initializers now), but its `targets` records
  still get their pointer fields symbolized.  The room lists above are C
  since #36 phase 2, and their entry still marks the 333 RoomDefs.

When the table points at addresses that have no label yet, run the
splitter with `--missing-labels`; it writes the `data_symbols` entries
that would label every target:

```sh
docker run --rm -v "$PWD":/src -w /src knidl-builder \
  python3 tools/split.py --rom baserom.gba --config tools/split_config.json \
  --missing-labels pending/missing.json
```

Review the list (which segments the targets fall in), merge it into
`data_symbols`, run `make split` and `make clean && make compare`.

### 3.3 Excluding a word

`not_pointers` maps a word address to the reason it must stay inside the
`.incbin` although rule 2 or 3 would symbolize it:

```json
"not_pointers": {
  "0x0872EA04": "sram_driver_fn_table[0] = ReadSram_Core+1, which src/agb_sram.c defines static ..."
}
```

The two entries today are the SRAM driver table's pointers to the SDK's
two `static` RAM-copied cores, which no global symbol can name (4.116).
A coincidental value (a number that happens to equal a function entry)
in a non-asset segment would go here too; none is known.

## 5. Proven pointers and coincidences

A word is symbolized only when it is *proven* to be a pointer:

- its value (with the Thumb bit) is a symbols.csv function entry, in a
  non-asset segment; seg 18's 2,700 such words sit in pointer runs or are
  fields of fixed-layout records (lesson 4.118), and the task-type table's
  266 are also a proven `pointer_tables` entry; or
- it is a pointer field of a `pointer_tables` entry, whose `why` names
  the consumer.

A value that merely lies in `0x08000000-0x08800000` is *pointer-like*, not
a pointer. The C types are part of the proof, not all of it: most seg 18
tables are declared `u32 []` by their consumers, which says nothing about
their words, and a declared `T *x[]` proves the element type but not the
extent.

### 5.1 The next-label extent (a heuristic, counted apart)

For an array the consumer declares as `T *gUnk_X[]` (or `[N][M]` of
pointers) without a usable length, a `"extent": "next-label"` table runs
from its label up to the next label of its segment (or the segment's
end). `make split` accepts it only if **every word of that span is NULL
or a pointer value** (ROM, EWRAM or IWRAM), so a declared pointer array
followed by other data is refused rather than truncated by guesswork, and
every RAM target must already be a named cell. Phase 1 applies it to the
48 clean tables of seg 18 (1,591 ROM pointers, 20 RAM pointers, 462 new
labels); `make datastats` counts their words on a line of their own.

The failure mode: an unlabeled neighbour table that is also all pointers
is absorbed into the span. The bytes are unaffected (every word is still
the pointer it was), but the table's documented EXTENT is then wrong. A
new label at the neighbour's start shrinks the span automatically on the
next `make split`, so the fix is always a label, never an edit.

### 5.2 Functional tables in C (`src/data/`, phase 2)

A table whose layout its consumer proves can leave the data segments and
become a typed C definition in `src/data/<name>.c` (katam's `src/data/` is
the model, without its converted assets):

1. write the C: the table's `const` objects in address order, one entry
   per line, every pointer by its symbol (functions, labels of the data
   files, other C tables), the element type the consumer's header
   declares.  A C initializer with more than 256 numbers carries a
   `data-policy: functional <why>` comment (§6);
2. verify it against the ROM exactly like a function:
   `./tools/fnmatch.sh <start> <end> src/data/<name>.c --rodata`
   (links the object's `.rodata` at `<start>` with stand-ins and compares);
3. `python3 tools/carve_data.py <start> <end> <name> --write` cuts the
   range out of the data segments (it may span two adjacent ones), adds a
   `c_data` row to `segments.txt` and adds a `linker.ld` block for
   `build/src/data/<name>.o(.rodata)` with the matching-mode assertion
   of `<start>` (section 8.2).  It
   refuses asset segments and prints the labels the C must define, in
   order;
4. `make split && make clean && make compare`.

`tools/split.py` treats a `c_data` row as C-owned: its `data_symbols` are
C symbols (they leave `asm/rom_syms.s`; absolute stand-ins exist only for
its own verification link), a `pointer_tables` entry inside it emits no
words but still marks its `targets`, and a next-label extent inside it
stops at the next C-defined symbol.  The header that declares the table
spells it `const` (the consumers compile to the same assembly).

| table | range | C | consumer (the layout proof) |
|---|---|---|---|
| `gTaskTypes[266]` | `0x0872FF30-0x08730780` | `src/data/task_types.c`: `{taskClass, {0, 0, 0}, (u32)Task_X}` per type | `TaskCreate` (`src/early_5654.c`) copies `.taskClass` into the task and `.entry` into `gTaskResumeAddrs[]`, which the ARM switcher enters (rom-map §6) |
| the six `struct ActorDef *` tables | `0x0873ECEC-0x0873EEA0` | `src/data/actor_defs.c` | `sub_08063704` (`src/actor_63698.c`) binds a task to `table[Task.unk76]`, the table picked by `Task.actorKind`; lengths are the next-label spans (§5.1) |
| `gRoomTable[9][8]` | `0x087E1D58-0x087E1E78` | `src/data/room_table.c` | the room loaders read `gRoomTable[level][stage][room]` into `gCurRoomDef` (`src/level_23948.c`, `src/level_242d0.c`) |
| the 57 stage room lists | `0x087E1F58-0x087E2570` | `src/data/room_lists.c` | the same loaders index them with `gRoomIndex`; each ends with a NULL |

What they point at stays where it is: the ActorDef records (seg 18,
interleaved with other tables in 33 runs) and the RoomDefs (`room_data`)
are structure-only data, declared in `include/actor.h` and
`include/room.h`; the maps and graphics behind the RoomDefs are assets.

symbols, 0x113C bytes, 763 pointer words) apart from the data files.

Most of the remaining "points at code" words are coincidences inside
assets (7,772 in `level_graphics_palettes` alone) and in seg 18's byte
tables (`0x08080808` runs); the "points at data" words are seg 18's
data-to-data tables (18,617), seg 19's songs (11,161) and the graphics
zones. `make progress`'s last line counts `.incbin` slices: under this
design their number goes **up** as labels go in (5,963 today, down from
6,295 after phase 1 because the C tables took 333 slices with them; 19
before), while their bytes go down by four per symbolic word (lesson
4.120).

`make check-data` (`tools/check_data_policy.py`, run in CI on every
push, no baserom needed) enforces the policy: data segments live in
`data/`; a `data/*.s` line is a comment, `.section`, `.global`, a label,
`.incbin "baserom.gba", <offset>, <length>`, `.word <symbol>[+n]` or an
alignment directive; `.incbin` anywhere names only `baserom.gba`; no
asset-format file (PNG, palettes, tile/LZ/`.bin` blobs, MIDI, AIF/WAV/PCM,
...) and no binary file is committed; no hex dumps; and a C initializer
with more than 256 numbers must carry a `data-policy: functional <why>`
comment within the three lines above it. The hex-dump rule still applies
inside such a table, so write it one entry (or at most 16 values) per line. Where assets end and functional
tables begin is a judgement the check cannot make: reviewers make it,
using §1. Code segments' literal pools and raw instruction halfwords are
code and outside its scope.
