# ROM data: structure, not bytes

This page is the convention for the ROM's data (issue #36). The code side
of the project is finished (every game function is byte-exact C, see
AGENTS.md). The data side works differently, because of the data policy.

## 1. The policy

The repository is public. The rule is in AGENTS.md ("Data policy"). It
follows the zeldaret/mzm line, which was chosen after comparing what the
other decompilations do with the ROM's data (surveyed on #36):

| project | data not yet understood | tables a consumer proves | graphics, audio, text, maps |
|---|---|---|---|
| katam (Kirby & The Amazing Mirror) | label + `.incbin "baserom.gba"` slices | committed as C with values | committed, converted (PNG, MIDI, AIF) |
| pret (pokeemerald ...), sa2, fireemblem8u | a few baserom slices, or none | committed as C with values | committed, converted |
| tmc (Minish Cap), mzm (Zero Mission) | none left | committed as C with values | **not committed**: extracted from the baserom at build time (tmc's JSON asset manifests, mzm's `tools/extractor.py`) |
| sm64, OoT (N64) | - | committed as C | **not committed**: extracted from the baserom at build time |

So this project draws the same line as tmc, mzm, sm64 and OoT:

- **Assets are never committed, in any form.** That covers graphics
  (tiles, tilemaps, palettes, sprite frames), audio (samples, songs), text
  and fonts, and level layouts and maps. They stay `.incbin
  "baserom.gba", <offset>, <length>` slices, read from the user's own
  dump. If they are ever made editable, that happens through build-time
  extraction into gitignored directories, never by committing converted
  files.
- **Functional data may be committed as C** once a decompiled consumer
  proves its layout: pointer tables, task/actor/object definitions,
  animation and frame tables, parameters. It gets typed, named fields,
  exactly like the decompiled code.
- **Until then, data is committed as structure only**. That is what
  `make split` emits today, and what the rest of this page describes.

What a data change commits is *structure*:

- **labels** at table boundaries, so C references a real definition
  instead of an absolute `gUnk_08XXXXXX = 0x08...`;
- **pointer words as symbols**: `.word gUnk_0835DDC0`, `.word sub_0806xxxx+1`.
  A pointer says where a table points, which is structure, not content.
  It is also what will make the ROM shiftable (§6);
- **types**: C declarations proven by the decompiled consumers (phase 2);
- **build-time extraction**: every other byte stays
  `.incbin "baserom.gba", <offset>, <length>`, read from the user's own
  dump when the ROM is built. Only offsets and lengths are committed.

## 2. What `make split` emits for a data segment

Every `data`-kind row of `docs/analysis/segments.txt` (except the
hand-written cartridge header `asm/rom_header.s`) is configured in
`tools/split_config.json` and emitted by `tools/split.py` as
`data/<segment>.s` (or, for the pieces of a zone cut around C runs, as
one `.section` each of `data/<zone>.s`, #167; docs/splitting.md). `asm/` holds code only. A generated data file contains
nothing but:

```
@ Auto-generated by tools/split.py from baserom.gba - DO NOT EDIT.
@ ... header: range, counts, the asset note ...
	.section .room_bg_anim_lists, "a"
	.global	room_bg_anim_lists
room_bg_anim_lists:
	.global	gUnk_087E1E78
gUnk_087E1E78:
	.word	gUnk_083356E0
	...
	.incbin	"baserom.gba", 0x7E1EA0, 0x4
```

The emitter's rules, in order:

1. **Labels.** A `.global` label at every ROM `data_symbols` value and
   every `extra_labels` address inside the segment. Their absolute
   definitions leave `asm/rom_syms.s`, which keeps only RAM/I-O cells
   (and would list a ROM table only while it waits for its label).
   Several names at one address are fine (`gUnk_080CFE20` and
   `gSramIdString`).
2. **Code pointers.** A 4-aligned word whose value is a
   `docs/analysis/symbols.csv` function entry becomes `.word <fn>+1`
   (Thumb, value odd) or `.word <fn>` (ARM, value even), in every segment
   that is not an asset (§4). An even value equal to a *Thumb* entry is a
   `mov pc` jump-table target (lesson 4.38), and a relocation against a
   C-defined Thumb function would set bit 0, so it is never symbolized.
3. **Data pointers**, only inside a `pointer_tables` entry: a table whose
   layout a decompiled consumer proves (§5), or whose element type the
   consumer declares and whose extent is the span up to the next label
   (§5.1). Every non-NULL pointer word of it must resolve to a function, a
   ROM data label or a named RAM cell; `make split` stops on the first
   unresolved one (§3.2). NULL words stay inside the `.incbin`.
4. **Everything else** is `.incbin`, whatever its length (four bytes of a
   count between two pointers included).

A word that would need a label strictly inside it (at `addr+1..addr+3`)
stays inside the `.incbin`; inside a pointer table that is an error.

The verification is the one every split file gets: the whole group is
assembled, linked at the segments' VMAs with `asm/rom_syms.s` and
stand-ins for C-defined symbols, and compared with the baserom. A data file
cannot fall back to raw bytes (there are no instructions to demote), so a
mismatch is a planning bug and stops the run. `make compare` remains the
real proof (lesson 4.116: the stand-ins also resolve names the real link
cannot).

## 3. Adding structure

All of it goes through `tools/split_config.json`, never through the
generated files: CI re-runs `make split` and fails on any diff under
`asm/` or `data/` (lesson 4.11).

### 3.1 A label

Add `"0xADDRESS": "gUnk_ADDRESS"` to `data_symbols` (sorted by address;
`tools/addsyms.py` does this from a link's `undefined reference` wall).
A ROM address inside a data segment becomes a real label with the next
`make split`. Renaming (`gUnk_` to a real name) is #155's job; the address
is the key, so a rename is one value change.

### 3.2 A pointer table

Add an entry to `pointer_tables`:

```json
{
  "start": "0x087E1F58",
  "end": "0x087E2570",
  "why": "the stage room lists gUnk_087E1D58[level][stage] points at: ...",
  "targets": {
    "pointers": ["0x08", "0x0C", "0x10", "0x18", "0x1C", "0x20",
                 "0x28", "0x2C", "0x30", "0x44", "0x48"],
    "why": "struct RoomDef (0x58 bytes, M07, src/room_bg_layout.c): ..."
  }
}
```

- `start` plus `end` or `count`; `stride` (default 4) and `pointers`, the
  byte offsets of the pointer fields inside one element (default `["0x0"]`),
  describe an array of records: the task-type table is
  `"count": 266, "stride": 8, "pointers": ["0x4"]`.
- `why` is required: the consumer that proves the layout (function and
  file, or a pret reference for SDK tables). A table whose layout no
  decompiled code proves does not go in, however pointer-like its words
  look (§5).
- `targets` (optional, one level) says that every non-NULL word of the
  table points at one record of this layout, whose pointer fields are
  pointer words too. The room lists use it for their `RoomDef` headers.
- `"extent": "next-label"` replaces `end`/`count` for a plain array of
  pointers whose length no consumer gives (§5.1). Its `why` cites the
  declaration (`file:line` and the `extern`).
- A table that has moved to C (§5.2) keeps its entry: its own words are
  not emitted (they are C initializers now), but its `targets` records
  still get their pointer fields symbolized.  The room lists above are C
  since #36 phase 2, and their entry still marks the 333 RoomDefs; since
  #167 the RoomDefs are C too, and the entry documents their layout.
- `targets` may add `"tagged": {"0x0": ["0xC", "0x10"]}`: the field at
  `0x0` carries a flag in bit 0 (it is emitted as `label+1` when set),
  and a record whose flag is set has the listed extra pointer fields (the
  20-byte player frame records, `PlayerLoadFrameTilesAndPalette`,
  `src/player_helpers.c`).
- `"proof": "format"` marks a table that only a format parse proves and
  no code reads (§5.3); `make datastats` counts its words on a line of
  their own.  The default is `"consumer"`.
- A label strictly inside a pointer word (the C declares a table from a
  mid-word address: `gUnk_0875841E`, inside the fifth word of
  `gUnk_087583CC`'s row 2) is written after the word as
  `.set name, . - k`, which keeps it a section-relative symbol.

When the table points at addresses that have no label yet, run the
splitter with `--missing-labels`; it writes the `data_symbols` entries
that would label every target:

```sh
docker run --rm -v "$PWD":/src -w /src knidl-builder \
  python3 tools/split.py --rom baserom.gba --config tools/split_config.json \
  --missing-labels pending/missing.json
```

Review the list (which segments the targets fall in), merge it into
`data_symbols`, run `make split` and `make clean && make compare`.

### 3.3 Excluding a word

`not_pointers` maps a word address to the reason it must stay inside the
`.incbin` although rule 2 or 3 would symbolize it:

```json
"not_pointers": {
  "0x0872EA04": "sram_driver_fn_table[0] = ReadSram_Core+1, which src/agb_sram.c defines static ..."
}
```

Since #36 phase 2 run 2 the entries are the two value words of the BG
animation scripts' op 5 (a collision tile, not a pointer; the scripts
are C since #167, where the two words stay numbers), and since #167 the
word at `0x087404CC`: four `struct M19Frame` bytes `{8, 1, 0, 8}` of
`gUnk_087404A0` that equal `MasterIsr`'s address, which the
function-entry rule had written as `.word MasterIsr`.  The SRAM
driver table's two pointers to the SDK's RAM-copied cores used to be
here (lesson 4.116); `src/agb_sram.c` now gives the cores external
linkage, so they are symbols.

### 3.4 The m4a song structure (config `"m4a"`)

The songs are assets, but their pointers are structure, and a table of
a few thousand hand-written slots would duplicate what the format
already says.  So the config names only the roots:

```json
"m4a": {
  "why": "...",
  "song_tables": [
    {"start": "0x0860B460", "count": 579, "stride": 8, "why": "gSongTable ..."},
    {"start": "0x0872EB38", "count": 479, "stride": 8, "why": "gSfxTable ..."}
  ]
}
```

and `tools/m4a_struct.py` walks everything they reach with this ROM's
engine: song headers, the track event streams (the command set and the
operand counts come from `gMPlayJumpTableTemplate`, MPlayExtender,
MPlayMain's dispatch and the `ply_*`/xcmd handlers, not from pret's
tables), voicegroups (extent: the highest program a `VOICE` command
selects), drum kits (the key range the notes use), `WaveData` (the size
field) and the 4-bit CGB waves.  Every structure it parses is re-encoded
from its fields and compared with the ROM; a mismatch stops `make
split`.  `split.py` then labels every target (`gSong_`, `gSongTrack_`,
`gSongLoc_`, `gVoiceGroup_`, `gWave_`, `gProgWave_` + address; a
`data_symbols` name at the same address wins) and emits every pointer
field as a `.word`, the GOTO/PATT operands at any alignment (gas and ld
relocate an unaligned `R_ARM_ABS32`).  The numbers: 330 song headers,
701 tracks, 5 voicegroups, 129 `WaveData` (not 100, as §4.1 said
before), 3,894 pointer words (1,343 unaligned) and 2,156 labels.

### 3.5 Code of the other ISA (`isa_ranges`) and constant words (`raw_words`)

`"isa_ranges": [{"start", "end", "isa", "why"}]` marks code inside a split
function whose ISA is not the function's: the ARM islands of m4a_1's
Thumb functions (`__umul3232H32` in `umul3232H32`, and SoundMainRAM's
reverb loop and sample mixer, entered by `adr rN, <label>; bx rN` and left
by `adr r0, <thumb label>+1; bx r0`).  split.py decodes, labels and emits
them in that ISA, with `.arm`/`.thumb` at each boundary, so their
branches and `adr`s are labels inside the file.  Until #37 the mixer was a
`raw_ranges` entry kept as raw halfwords, because its Thumb decode read
one ARM instruction as a branch into another object, which a shifted ROM
would have rewritten (lesson 4.134); the census now sees the islands
through the ELF's `$a` mapping symbols like any other ARM code.

`"raw_words": {"0x<addr>": "<reason>"}` names literal-pool words of split
code that are constants, not addresses (m4a's `ID_NUMBER`, the
`SoundInfo.pcmBuffer` offset, `PCM_DMA_BUF_SIZE`, the sound DMA control
word): they stay numbers, emitted with a same-line `@ raw: <reason>`, the
justification `make audit` reads (docs/audit.md).

## 5. Proven pointers and coincidences

A word is symbolized only when it is *proven* to be a pointer:

- its value (with the Thumb bit) is a symbols.csv function entry, in a
  non-asset segment; seg 18's 2,700 such words sit in pointer runs or are
  fields of fixed-layout records (lesson 4.118), and the task-type table's
  266 are also a proven `pointer_tables` entry; or
- it is a pointer field of a `pointer_tables` entry, whose `why` names
  the consumer.

A value that merely lies in `0x08000000-0x08800000` is *pointer-like*, not
a pointer. The C types are part of the proof, not all of it: most seg 18
tables are declared `u32 []` by their consumers, which says nothing about
their words, and a declared `T *x[]` proves the element type but not the
extent.

### 5.1 The next-label extent (a heuristic, counted apart)

For an array the consumer declares as `T *gUnk_X[]` (or `[N][M]` of
pointers) without a usable length, a `"extent": "next-label"` table runs
from its label up to the next label of its segment (or the segment's
end). `make split` accepts it only if **every word of that span is NULL
or a pointer value** (ROM, EWRAM or IWRAM), so a declared pointer array
followed by other data is refused rather than truncated by guesswork, and
every RAM target must already be a named cell. Phase 1 applies it to the
48 clean tables of seg 18 (1,591 ROM pointers, 20 RAM pointers, 462 new
labels); `make datastats` counts their words on a line of their own.

The failure mode: an unlabeled neighbour table that is also all pointers
is absorbed into the span. The bytes are unaffected (every word is still
the pointer it was), but the table's documented EXTENT is then wrong. A
new label at the neighbour's start shrinks the span automatically on the
next `make split`, so the fix is always a label, never an edit.

### 5.2 Functional tables in C (`src/data/`, phase 2)

A table whose layout its consumer proves can leave the data segments and
become a typed C definition in `src/data/<name>.c` (katam's `src/data/` is
the model, without its converted assets):

1. write the C: the table's `const` objects in address order, one entry
   per line, every pointer by its symbol (functions, labels of the data
   files, other C tables), the element type the consumer's header
   declares.  A C initializer with more than 256 numbers carries a
   `data-policy: functional <why>` comment (§6);
2. verify it against the ROM exactly like a function:
   `./tools/fnmatch.sh <start> <end> src/data/<name>.c --rodata`
   (links the object's `.rodata` at `<start>` with stand-ins and compares);
3. `python3 tools/carve_data.py <start> <end> <name> --write` cuts the
   range out of the data segments (it may span two adjacent ones), adds a
   `c_data` row to `segments.txt` and adds a `linker.ld` block for
   `build/src/data/<name>.o(.rodata)` with the matching-mode assertion
   of `<start>` (section 8.2).  It
   refuses asset segments and prints the labels the C must define, in
   order;
4. `make split && make clean && make compare`.

`tools/split.py` treats a `c_data` row as C-owned: its `data_symbols` are
C symbols (they leave `asm/rom_syms.s`; absolute stand-ins exist only for
its own verification link), a `pointer_tables` entry inside it emits no
words but still marks its `targets`, and a next-label extent inside it
stops at the next C-defined symbol.  The header that declares the table

### 5.3 Format-only pointers (no consumer)

Two structures of the ROM have pointers that no code reads: the frame
lists (`sprite_frame_lists`, `0x087E2570`, and its twin at the end of the
player frame records, `0x0876923C-0x0876B1FC`) and the `GfxHeader`
trailer word at `+0x10` that points at each list.  Every `GfxHeader`
reader stops before `+0x10`, and no literal pool or table reaches the
lists.  Their format evidence is strong: each list is pointed at by one
trailer whose frame count equals the list's length, its entries are
strictly increasing, and almost all of them are exactly the labeled
address of a frame that a consumer proves (an OAM template stream or a
`struct TaskGfx` record).  They are symbolized for consistency (so tools
and modders see the structure), in `pointer_tables` entries marked
`"proof": "format"`, and only entries whose target is a consumer-proven
frame label or parses as a frame of the same sheet; `make datastats`
counts them apart.  Since no code reads them, a wrong one could not
change a shifted ROM's behaviour, but the rule stays the same as for any
pointer: no evidence, no symbol.

code and outside its scope.

## 8. Shifting the ROM

The goal of phase 2 run 2: a ROM whose sections can move, so that a
table, a sprite or a song can grow without breaking every pointer behind
it.  Two things decide it: whether the link places the sections itself
(8.2), and whether every pointer INTO the moved part is a symbol, which
the shift test measures and the census explains (8.1, 8.3).

### 8.1 The shift test (`make shifttest`)

`tools/shiftcheck.py` links the same objects twice: once as `make` does
(image A), and once with 0x1000 bytes of padding inserted in front of a
section (image B, `--defsym MATCHING=0`).  Every 4-aligned word of A whose
value (bit 0 cleared) points at or after the insertion point must read
value + 0x1000 in B:

- **relocated**: it does, the linker moved it (a `.word` symbol, a C
  initializer or a literal pool entry);
- **unrelocated**: it reads its old value, a number the linker never saw:
  a real pointer still written raw, or a coincidence (pixels, a value
  field) that only looks like an address;
- **broken** / **wrong**: neither, or a word that pointed before the
  point but moved (a `symbol+offset` across the point); both fail the
  target.  "other" counts the bytes that differ outside those words: the
  relative branches across the point and the unaligned m4a track operands
  (1,488 after crt0), which move correctly;
- **branches** (since run 3): `tools/branchcheck.py` decodes every
  relative branch that crosses the point (ARM B/BL, the ARM after
  `bx pc`, Thumb BL, B and B<cond> into code) and checks that image B
  still reaches the moved target.  No word compare can see a raw one
  (8.4); a bad one fails the test.  After crt0: 4 of 4.

The default points are the start of AgbInit (everything after crt0
moves, so it tests every word of the ROM), right after the code and the
SDK tables (`sram_id_string`), the room data, the compressed graphics,
inside the song zone, seg 18 (`engine_rodata`) and the player frame
records; `--at <section>` picks others.  No emulator is involved, and
the result is exact about what moved.  `make shifttest` then runs the
census (8.3) with `--strict`, which fails on any proven pointer or
unknown word; CI runs both after `make compare`, then the boot test
(8.4), and puts the tables in the step summary.

### 8.2 The linker: sections follow each other

`linker.ld` pins only the cartridge header (`0x08000000`: the hardware
reads it there, and its first word branches to the 0xC0 bytes after it).
Every other section is placed by ld right after the previous one, aligned
to its input sections; the order and the sizes alone give the original
ROM (lesson 4.133).  Each block is followed by the address the original
has:

```
    .agb_init : {
        build/src/agb_init.o(.text)
    } > ROM
    ASSERT(!MATCHING || ADDR(.agb_init) == 0x08000310, "MATCHING: .agb_init moved")
```

The Makefile links with `--defsym MATCHING=1` unless `MATCHING=0` is
given, so `make`, `make compare` and CI still fail at the first section
that moved, while a modified ROM links with `make MATCHING=0`.  The ROM
region is 32 MiB, and a last assertion checks that the matching image
ends at `0x08800000`.  `tools/ldblocks.py` writes blocks in this form for
`carve.py`, `carve_data.py` and `resegment.py`.

A group of rows (`tools/ldgroup.py`, §5.2) is one block that lists
several segments' input sections in order, with one assertion per row
on its first symbol (`ASSERT(!MATCHING || actor_rodata_0873f4c8 ==
0x0873F4C8, ...)`).

No zone keeps a pin for a pointer reason: since run 3 the census has no
proven pointer left raw and no unknown word (8.3), so every insertion
point is proven safe, and the boot test (8.4) runs shifted images at all
seven default points.

**The unreachable class** (run 3, counted apart): a word in bytes that
nothing can read.  A provider claims the region with kind
`"unreachable"` only if all of these hold, and its `why` records the
evidence (`build/ptrcensus_unreachable.json` lists every word with it):

- (a) no symbol, pointer word, pool literal or C initializer anywhere in
  the ROM points into the region.  `ptrcensus.py` checks this itself and
  stops on a failing claim: no 4-byte value at any byte offset outside
  the region points into it (bytes proven coincidences excepted, since
  they are proven not to be pointers), and no ELF symbol lies in it
  (except the segment-name label `split.py` writes at a data file's
  start, which names a file, not an object);
- (b) no consumer-proven extent, and no table indexed without a bound,
  can reach it: the `why` names the neighbouring tables and why each
  one's index or extent stops before the region;
- (c) the tool records it with that evidence.

A word nobody reads cannot break a moved ROM, whatever it is; the class
never symbolizes anything.  Unreachable words do not block an insertion
point.

### 8.4 The boot test (`make boottest`)

The shift test proves which words the linker moves; the boot test runs
the shifted images and watches the game.  `make boottest` links one
image per insertion point (`tools/boottest.py`, the shift test's image B:
the same objects, `linker.ld` with 0x1000 bytes in front of the section,
`--defsym MATCHING=0`, into `build/boottest/`), then runs `knidl.gba` and
every shifted image in lockstep in mGBA (`tools/boottest/boottest.c`
against mGBA 0.10.5's core library, built from the release tag in its own
image, `tools/boottest/Dockerfile`, so the toolchain image stays lean).
All cores get the same scripted input, one run per script of
`BOOTTEST_INPUT` (below), each from boot with an empty save held in
memory (no `.sav` is ever written), on the HLE BIOS; every frame compares
the video buffer, the audio samples and
EWRAM + IWRAM, where a RAM word may differ only by exactly the padding and
only if it points at or after the insertion point (a pointer the linker
moved, a return address on the stack).  The run fails at the first frame
that differs and prints it with both PCs and the script's scene;
`--step <frame>` then walks that
frame an instruction at a time and prints the last PCs before the
registers part.  Hashes are compared at run time only: no frame, frame
hash, savestate or recording is written or committed.  `--shot` writes
PNG frames of the reference for tuning a script, under `pending/` only.

```
make boottest                                  # every script, every point
make boottest BOOTTEST_AT="agb_init"           # one point
make boottest BOOTTEST_INPUT=tools/boottest/subgames.txt   # one script
make boottest BOOTTEST_FRAMES=3000             # shorter runs
make boottest-coverage                         # the coverage figure (below)
```

**Checkpoints.**  A script names its scenes and proves them:
`mark <scene>` names the scene that starts there (the run prints each
one with its frame, and a difference is reported with its scene), and
`expect <cell> <op> <value>` reads a RAM cell of the reference there
(`<symbol>[+offset]:<size>` or `0xADDR:<size>`, size 1, 2 or 4; `==`,
`!=`, `<`, `<=`, `>`, `>=`, unsigned).  Both sit between steps, outside
`repeat` blocks, and take effect at the frame where the next step
starts.  The symbols come from `build/boottest/syms.txt`, the ELF's `nm`
list, which `boottest-roms` writes.  A failed expectation fails the run
("SCRIPT DRIFT"): a script whose claims no longer hold (a changed menu
timing, an enemy that moves differently in a modified ROM) fails loudly
instead of playing on into a different game.  The scripts check the game
state, the menu screen, the level, stage and room indices, lives and
health, the sub-game index and phase, the win counters and race times,
the game-over cursor and score; they name `gUnk_` cells by address, with
the name in a comment, since `tools/rename.py` does not edit the scripts
(a renamed symbol fails the run with exit status 2, not silently).
Until #168, `input.txt`'s comments put each menu screen one key early
(its START at frame 500 is ignored: after a completed logo the title
reads keys only from about frame 570); two agents found it independently,
and the expects now pin the real screens.

**Tuning a script.**  `--shot F,...` / `--shot-every N` write PNG frames of
the reference and `--peek CELL,...` with `--peek-every N` prints RAM cells
(both diagnostics, local, under `pending/` only); the reference alone runs
at about 1,000 frames a second (Air Grind's per-scanline effects about
370).  What worked in #168: search for the first frame a menu accepts a
key (the presses sit there, and the expects catch a shift); start each
life's block on the frame Kirby drops back in, since enemies do not
repeat between lives; read the game's own tables for timing windows
(Bomb Rally's return windows, `0x087565F4`); move one hold or release at
a time in a closed loop for Air Grind's rail gaps.  Every input is
deterministic: the same script plays the same game in every run.

  (`src/main_hblank_bands_in_blend.c`) falls off its end without a return value on its
  last frame, and `UpdateHBlankScroll` (`src/room_gfx_spawns.c`) takes the
  function's own address, still in r0, as the HBlank DMA count
  (`gHBlankDmaCnt = 0xA2600000 | 0x6155`, and `gHBlankDmaSrc` from it).
  The ROM's own undefined behaviour, so a shifted image programs a
  different count for one frame (frame 1126, the game select menu); the
  picture and the sound stay identical.  The two cells are the only
  `--ram-allow` entries (`BOOTTEST_RAM_ALLOW` in the Makefile).

With the trampolines fixed, all seven points run the whole script with
identical video, audio and RAM (the two allowed words apart, after crt0
only) and identical emulator error counts (111 in every image).  The
errors are the game's own: the HLE BIOS warns about LZ77 streams whose
header promises more than the destination holds (`0x085BA25C` into VRAM,
`0x085BA4CC` and, in other scenes, `0x085B85A0`, `0x085E2CE0` and
`0x085E4064` into the decompression buffer), and mGBA logs reads of the
BIOS region through null pointers (`Bad BIOS Load8: 0x00000000`); the
count is compared, since a shifted image names other addresses.

#168's three new scripts added 29,447 frames: `subgames.txt`,
`gameover.txt` and `level1.txt` run at all seven points with identical
video, audio, RAM (the same two allowed words, after crt0 only) and
error counts (0, 225 and 173), and every expectation of every script
holds.  No shifted image differed, so the sub-games, the game over, the
goal games, the Warp Star, a mid-boss and stages 1-2 and 1-3 follow
every pointer they use correctly after a shift; the census had already
said so.

Timing does not enter: mGBA charges ROM wait states by region and
by sequential/non-sequential access only (`src/gba/memory.c`, 0.10.5), and
its prefetch model depends on PC distances, so the same code runs in the
same cycles at any address.  (On hardware a sequential burst crossing a
128 KiB boundary of the cartridge bus is non-sequential; a shift can move
those boundaries, which only timing-sensitive code would notice, and the
emulator cannot tell.)

What it proves and what it does not: it is empirical and only as wide as
the scripts.  Every pointer the reached code follows (code, tables, rooms,
sprites, the songs of the title, the story, level 1 and the sub-games,
the sound effects played) works shifted, at every point, so none of the
census's coincidence or unreachable words that these scenes read was a
real pointer.  Data the scripts never reach (levels 2-7, the bosses, the
arenas, the ending and the credits, the locked modes, link play) is
untested by them, and the census (8.3) remains the proof for those.  It is also the only check of what
the word compare cannot see: a relative branch written as raw bytes
(which `tools/branchcheck.py` now checks statically at every shift-test
point) and behaviour that depends on an address.

54, 31, 33 and 40 s (`level1.txt` at its first length, 9,671 frames;
about 55 s at 13,471), plus 9 s to link the shifted images: the
boot-test step went from about 60 s to 167 s with #168, about 180 s at
the final length (runners vary: another run took 39, 22 and 24 s for
the first three; the budget was 3 minutes more).  The emulator runs some 250-360 frames a second there with eight
cores.  Locally (8 threads) `make boottest` takes about 120 s with
both images built; the emulator image builds in about 90 s from
scratch.  All four scripts run on every push and pull request,
so no scheduled job is needed; a longer script (the level 1 boss, say)
would join `BOOTTEST_INPUT` the same way, or run on its own with
`make boottest BOOTTEST_INPUT=...`.  CI runs the test after `make
shifttest`, with the emulator image from the GitHub Actions layer cache
(`docker/build-push-action`, `type=gha`), so it is rebuilt only when
`tools/boottest/` changes.
